# NWIS — Nearby Wells Intelligence System (PS 26121)

One application: a FastAPI backend (`backend/`, port 8008) and a React frontend (`frontend/`, port 5173).

## Run it

```powershell
powershell -ExecutionPolicy Bypass -File .\start-nwis.ps1 -Install   # first time
powershell -ExecutionPolicy Bypass -File .\start-nwis.ps1            # afterwards
```

Or by hand:

```bash
cd backend  && python run.py          # http://127.0.0.1:8008  (API docs at /docs)
cd frontend && npm install && npm run dev   # http://localhost:5173
```

On every start the backend runs the pipeline itself: it generates any missing demo data, pushes the bundled sample reports through extraction into the knowledge archive, trains/benchmarks models whose metrics are missing, and runs the alert engine for the active well — so every screen is populated on first load. It is idempotent (nothing is duplicated on restart).

No accounts or API keys are needed. Everything runs locally; the only outbound calls are map tiles (OpenStreetMap / Esri).

## Demo walkthrough (about 5 minutes)

1. **Live well** — active well HGJ-012. Press *Start live stream*. The bit advances; NWIS warns before each depth where nearby wells had trouble (torque spikes in Barail coal, then the Kopili/Sylhet mud-loss zone near TD). Alerts pop up with a link to their evidence.
2. **Nearby wells** — drag the radius (1–60 km). Wells are ringed by their incident mix. Click HGJ-011 → its incidents by depth, what the crew did, and the source report page.
3. **Depth correlation** — wells aligned on the formation at the bit. Switch to *Measured depth* to see why raw MD comparison misleads.
4. **Ask the archive** — e.g. *“How were mud losses handled in nearby wells?”* The answer is composed only from records; every sentence cites them.
5. **Documents** — *Run a sample report* (`DDR_HGJ-011_2021-03-02.pdf`). Three incidents are extracted with depth, formation and crew action, and immediately become searchable and part of HGJ-011's record.
6. **Alerts** — why each alert fired, the offset-well evidence, what worked there, and acknowledgement with a note.
7. **Rig sensors** — inject *Lost circulation*; within seconds the sensor risk engine raises its own alert from flow-out, pit and pressure-window behaviour.
8. **Models & benchmarks** — measured accuracy of the three model families (offset-history hazard models, sensor risk engine, report extraction), including where the data is still too thin.

## What is real and what is simulated

| Part | Status |
|---|---|
| Offset ranking (DORS), stratigraphic alignment, risk corridors, alerts, grounded Q&A, extraction pipeline, sensor risk engine | Real code running on the data below |
| Wells, trajectories, formations, events (Upper Assam testbed) | Synthetic, internally consistent — `backend/app/data/synthetic/` |
| Casing/mud programs, extra torque/cementing/mud-loss events | Derived deterministically by `augment_demo.py` |
| Source DDR/WCR PDFs cited by events | Generated by `generate_source_documents.py` into `backend/app/data/source_documents/` |
| eRTMAC real-time feed | Simulated two ways: depth replay (`/api/v1/live/replay`) and physics digital twin (`/api/v1/physics/stream`) |
| Hazard ML models | Trained on the testbed (`ml/train_hazard_models.py`); hazards with < 8 examples use a labelled rule-based estimate |

To connect OIL data: replace the JSON files in `backend/app/data/synthetic/` (same schema, WITSML-aligned), point `source_documents/` at the DDR/WCR archive, and swap the replay/physics stream for the eRTMAC adapter. Uploaded reports flow into the archive automatically (`services/document_bridge.py`).
